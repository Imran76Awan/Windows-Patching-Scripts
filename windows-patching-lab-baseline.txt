WINDOWS PATCHING LAB BASELINE
Reference measurements behind the EndpointWeekly 40-part Windows patching
troubleshooting series (https://endpointweekly.com/blog.html).

WHAT THIS IS
  Read-only measurements taken from one live Windows 11 25H2 corporate device
  (build 26200.9168) while researching the series, plus the documentation
  contradictions and stale/incorrect published facts found along the way.
  Nothing here modified the device. Every entry is either a measurement or a
  citation.

HOW TO READ IT
  - Entries marked CORRECTION overturn an earlier claim in this same file.
    Later entries win; the superseded text is kept so the reasoning is visible.
  - Event and package COUNTS are point-in-time. Several grew between reads
    during a single session (Event 26 went 210 -> 1,815). Treat every count as
    "at time of measurement", never as a fixed value.
  - Items labelled "observed, not documented" were measured on the device but
    have no Microsoft reference page. Do not build compliance checks on them.
  - Build numbers here are specific to one device and one month. The mechanisms
    generalise; the numbers do not.

PRIVACY
  No machine name, user name, domain, serial number, IP address, tenant ID or
  device ID appears in this file. The only GUIDs are Intune/Autopatch service
  provider IDs, which are the same in every tenant.

*** POST-23: WHY StartComponentCleanup NEVER FINISHES ON A FLEET (documented) ***
  Measured Event 328 @ 2026-08-21 21:51:37: "Task Scheduler stopped instance of task
    \Microsoft\Windows\Servicing\StartComponentCleanup because computer is no longer
    idle." Killed 6m14s in. NO Event 201 or 102 => it never completed.
  ROOT CAUSE, documented: the task XML sets StopOnIdleEnd=true and RestartOnIdle=FALSE.
    Microsoft: "To terminate and restart a task, BOTH properties and elements must be
    set to True." Only one is set - so it terminates and never resumes.
  Next night's run COMPLETED but did nothing. Real CBS.log chain:
    Maint: launch type: ScheduledTask -> begin scavenge -> CSI "Store coherency cookie
    matches last scavenge cookie, skipping scavenge" -> "scavenge time so far: 0 seconds"
    -> "used space change: 1376 KiB, hr: S_OK". That 13-second no-op is what stamped
    "Date of Last Cleanup : 2026-08-22 13:37:36" with LastTaskResult=0.
    => a green task result does NOT mean cleanup happened.
  Task internals: <Triggers /> is EMPTY - driven only by MaintenanceSettings P7D/P14D.
    ExecutionTimeLimit PT1H (the documented 1-hour timeout, made visible).
    DisallowStartIfOnBatteries=true.
    Action is a COM handler, NOT an exe: CLSID {752073A1-...} "Component Based Servicing
    Session" -> AppID {752073A2-...} "Trusted Installer Service", LocalService=TrustedInstaller.
    Event 129 (process launch) appears 501x in that log and NEVER for this task.
  LastResetBase_UTC is ABSENT on this device - Microsoft's one documented value here, so

  wcp.dll = "Windows Componentization Platform Servicing API" (this IS CSI). Lives in the

*** POST-34: THE HOTPATCH BUILD INVERSION (counterintuitive - read carefully) ***
  Microsoft shipped TWO packages on 11 Aug 2026 for the same releases:
    KB5120994 (Hotpatch) -> 25H2 build 26200.9106, NO restart
    KB5121003 (LCU)      -> 25H2 build 26200.9168, restart required
  The HOTPATCHED device lands 62 REVISIONS LOWER than the rebooted one.
  => In a hotpatch month, a HIGHER UBR is evidence the device did NOT get the hotpatch.
